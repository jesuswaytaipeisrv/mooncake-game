# 設計決策

## 2026-09-16：沿用主持／玩家活動模式，但建立獨立遊戲狀態

- 狀態：已採用
- 背景：使用者指定參考提水長大與龍舟遊戲。
- 決定：沿用六碼房間、QR 加入、三隊自動分隊、手機連點、即時同步與 GitHub Pages 的使用流程；不直接共用舊遊戲狀態或畫面程式。
- 原因：保留熟悉的活動操作，同時避免舊版提水行程與月餅規則互相纏繞。
- 替代方案：直接複製提水遊戲並只改文字；修改較快，但會保留不合題的桶水、灌溉與成長計算，因此未採用。

## 2026-09-16：每隊只同步單一口數

- 狀態：已採用
- 決定：每隊只寫入 `biteUnits`；已吃月餅數、目前月餅比例、總進度與勝負門檻全部由純函式推導。
- 原因：降低多人同時點擊造成重複或矛盾狀態的風險，也便於單元測試。

## 2026-09-16：Firebase 初版預設停用

- 狀態：已取代
- 決定：新專案的 `firebase-config.js` 預設為空值，只使用本機示範模式。
- 原因：開發與自動化測試不應寫入既有活動資料；Firebase 專案與正式 rules 應在使用者確認後再連接。

## 2026-09-16：沿用活動 Firebase 的專屬子樹

- 狀態：已採用
- 背景：使用者確認沿用既有活動 Firebase；目前資料庫已部署提水遊戲的匿名讀寫規則，但月餅頂層路徑尚未獲授權。
- 決定：沿用 `dragon-boat-race` Firebase Web App，將月餅房間存放於 `water-splash-race/rooms/mooncake-feast-race/<房間碼>`。
- 原因：可立即使用既有匿名驗證與已部署規則，且月餅資料集中於固定子樹，不與六碼提水房間鍵混用，也不必冒險覆蓋共用資料庫的完整規則。
- 替代方案：在資料庫頂層新增 `mooncake-feast-race` 規則；需要 Firebase 管理權限並先匯出、合併線上完整規則，因此本次未採用。

## 2026-09-23：使用 Web Audio API 合成可靜音的遊戲音效

- 狀態：已採用
- 背景：遊戲需要每口咀嚼、85% 衝刺與獲勝歡呼音效，且活動現場必須能隨時靜音。
- 決定：由瀏覽器 Web Audio API 即時合成三種音效，不加入外部音效檔；主持與玩家各自控制音效，預設靜音並把選擇保存在本機瀏覽器。
- 原因：不增加下載、授權或第三方服務依賴，也不讓音效偏好污染多人遊戲狀態；由使用者操作開啟可符合行動瀏覽器的自動播放限制。
- 替代方案：提交 MP3／WAV 素材；音色更接近真人錄音，但會增加素材授權、檔案大小與載入失敗風險，因此本次未採用。
